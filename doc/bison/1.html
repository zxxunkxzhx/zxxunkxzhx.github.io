Token kind, value and name

The Bison representation for a terminal symbol is also called a token kind.

If you refer to .tab.h file, you will notice code like

#ifndef YYTOKENTYPE
# define YYTOKENTYPE
  enum yytokentype
  {
    YYEMPTY = -2,
    YYEOF = 0,                     /* "end of file"  */
    YYerror = 256,                 /* error  */
    YYUNDEF = 257,                 /* "invalid token"  */
    OB = 258,                      /* OB  */
    CB = 259,                      /* CB  */
    IDENTIFIER = 260               /* IDENTIFIER  */
  };
  typedef enum yytokentype yytoken_kind_t;
#endif

We normally can't define YYTOKENTYPE in .l or .y, bison or flex are not expecting we to do that.

If you refer to .tab.c file, you will notice code like

#include "parser.tab.h"
/* Symbol kind.  */
enum yysymbol_kind_t
{
  YYSYMBOL_YYEMPTY = -2,
  YYSYMBOL_YYEOF = 0,                      /* "end of file"  */
  YYSYMBOL_YYerror = 1,                    /* error  */
  YYSYMBOL_YYUNDEF = 2,                    /* "invalid token"  */
  YYSYMBOL_OB = 3,                         /* OB  */
  YYSYMBOL_CB = 4,                         /* CB  */
  YYSYMBOL_IDENTIFIER = 5,                 /* IDENTIFIER  */
  YYSYMBOL_YYACCEPT = 6,                   /* $accept  */
  YYSYMBOL_program = 7,                    /* program  */
  YYSYMBOL_block = 8,                      /* block  */
  YYSYMBOL_9_1 = 9,                        /* $@1  */
  YYSYMBOL_statements = 10,                /* statements  */
  YYSYMBOL_statement = 11                  /* statement  */
};
typedef enum yysymbol_kind_t yysymbol_kind_t;

note YYerror's symbol kind is not enumed as 256, so does YYUNDEF;

Each Special Tokens(refer to 4.3.2) are explained as followings:

  • YYEMPTY: bison don't need to know the look ahead in this case
  • YYEOF: bison trace "end of file" for this case(refer to enum yytokentype); in the case there are still inputs but we wanna stop parsing, .l can still return this value instead of -1(don't return YYEMPTY, it has special meaning)
  • YYerror: bison don't know what's the error, so .l must call yyerror() itself before bison entering recovery(in .y rule, you write `error` for YYSYMBOL_YYerror)
  • YYUNDEF: it's a "invalid token" to .l, bison call yyerror for "invalid token", then enters error recovery.

A token has kind, and value, location, etc; for here, any formal grammar only need the kinds as place holders, for example, if a rule mentions the terminal symbol ‘integer constant’, it means that any integer constant is grammatically valid in that position.

A terminal symbol can also be represented as a character literal, just like a C character constant. These kinds of tokens has their kind as the character's ascii value, and, these kinds of tokens normally don't have|need values; note yylex return 0 when no more inputs or wanna stop, so the null char can't be a Character token.

A third way to represent a terminal symbol is with a C string constant containing several characters, these kinds of tokens normally have constant values.

The basic way to declare a token kind is `%token name`; Alternatively, you can use %left, %right, %precedence, or %nonassoc instead of %token.

(zxxu)by default, a token's name is simly string repr of its kind, but we can specify string alias(refer to 3.7.2); With and only with %token, you can set string alias for tokens

For example for `%token ARROW "=>"`, you can use ARROW or "=>" interchangeably in .y, and ARROW in .l(or TOK_ARROW assuming you added `%define api.token.prefix {TOK_}`)

augmented start rule

bison parser's first rule is always
 $accept: program $end
It's internally named augmented start production

(LR) item

An item is a production with a distinguished position (the "dot") in its right-hand side(indicating how much of the production has been recognized).

Starting from kernel items, non-kernel items are added to a state during the closure operation, which complete the item set of a state.

Note we're mentioning LR(0) closure here, for LR(1) closure, a lookahead terminal (or $end) must be given.

Any kernel item must have at least one symbols recognized, except for `$accept: • start-symbol $end`, which is the unique kernel item of state 0

lookahead

When a token is read, it is not immediately shifted; first it becomes the lookahead token, which is not on the stack.

The lookahead token is stored in the variable yychar. Its semantic value and location, if any, are stored in the variables yylval and yylloc.

conflicts

reduce/reduce conflict happens when the LR(1) parsing algorithm is not able to decide which reduction to apply.

shift/reduce conflict happens when don't know whether to apply a reduction or read more of the input; note if a state has shift action(on lookahead), there won't be conflicts.

reducing, by example `expr → expr + expr`

  1. Execute: $$ = $1 + $3;
  2. Pop symbols: expr + expr
  3. Reveal the previous state: pop same number of states
  4. push expr; yystate = goto(previous_state, expr); go-to/jump-to yystate

midrule action

A midrule action may refer to the components preceding it using $n

zxxu: bison make an augmented production `$@n: %empty` for midrule action.

consistent state and defaulted state

A consistent state is a state that has only one possible parser action. If that action is a reduction and is encoded as a default reduction(later will introduce), then that consistent state is called a defaulted state

accepting state

accepting state is the default state with its rule as accept reduction, that is, `$default accept`

any bison parser exit in following way:

...
the state stack now is [0,]; the symbol stack is now [start-symbol,]
(the parser has just performed a reduction whose LHS is the start symbol, so)
goto the pre-accept-state(zxxu's definition) which has and only has a shift action for $end
shift $end and enter the accepting-state
the parser(compiled with bison --debug option) will trace like：
    Stack now 0 pre-accept-state accepting-state
the parser then finalize like:
    Stack now 0 pre-accept-state accepting-state
    Cleanup: popping token "end of file"...
    Cleanup: popping nterm // poping the start-symbol nonterminal

5.8.2 default-reduction

After parser table construction, Bison identifies the reduction with the largest lookahead set in each parser state. To reduce the size of the parser state, traditional Bison behavior is to remove that lookahead set and to assign that reduction to be the default parser action. Such a reduction is known as a default reduction.

unless we %define lr.default-reduction as "consistent" or "accepting"(accepting state), else default-reduction is "most"(most aggressive)

Following is an example

start:
      stmt
    ;

stmt:
      x 'A'
    | x 'B'
    | x 'C'
    | y 'D'
    ;

x: %empty ;

y: %empty ;
closure of state 0 is:
    0 $accept: • start $end
    1 start: • stmt
    2 stmt: • x 'A'
    3     | • x 'B'
    4     | • x 'C'
    5     | • y 'D'
    6 x: ε •
    7 y: ε •
we have two candidates to default-reduction, item 7 or item 6; as 6 has its lookahead set size as 3 which is larger than 1(use --report=lookahead to show this set), so the action table is:
    'D'       reduce using rule 7 (y)
    $default  reduce using rule 6 (x)

    start  go to state 1
    stmt   go to state 2
    x      go to state 3
    y      go to state 4
note a state can be shifted while having default-reduction(refer to state 8 of `8.2 Understanding Your Parser`)
