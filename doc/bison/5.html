The precedence of a rule

By default, the precedence of a rule is that of its last token; the resolution of conflicts works by comparing the precedence of the rule being considered with that of the lookahead token(If either the rule or the lookahead token has no precedence, then the default is to shift).

If the token's precedence is higher, the choice is to shift; If the rule's precedence is higher, the choice is to reduce. If they have equal precedence, the choice is made based on the associativity of the lookahead token: if %left, reduce; else if %nonassoc, error(declares that it is a syntax error to find the same operator twice "in a row"); else shift.

The last alternative, %precedence, allows to define only precedence and no associativity at all; As a result, any associativity-related conflict that remains will be reported as an compile-time error(zxxu: if associativity is involved, you have to specify either %left, %right or %nonassoc)

Context-Dependent Precedence

The Bison precedence declarations can only be used once for a given token. For context-dependent precedence, you need to use an additional mechanism: the %prec modifier for rules. Following is how %prec solves the problem of unary minus:
	…
	%left '+' '-'
	%left '*'
	%left UMINUS
Now the precedence of UMINUS can be used in specific rules:
	exp:
	  …
	| exp '-' exp
	  …
	| '-' exp %prec UMINUS

.xml output

Besides --verbose for textual output and --graph for DOT output, another alternative is to output an XML(--xml[=FILE]) file that may then be, with xsltproc(apt -y install xsltproc), rendered as either a raw text format equivalent to the verbose file, or as an HTML version of the same file(note newer bisons supports --html), with clickable transitions, or even as a DOT. The .output and DOT files obtained via XSLT have no difference whatsoever with those obtained by invoking bison with options --verbose or --graph.

following is the steps to produce a html output:

  1. bison -d --verbose --warnings=all --xml data_swap_demo.y
  2. find a path by calling `bison --print-datadir`, normally the path is /usr/share/bison
  3. xsltproc /usr/share/bison/xslt/xml2xhtml.xsl data_swap_demo.xml >data_swap_demo.html

to produce DOT file, change xml2xhtml into xml2dot

Tracing Your Parser

There are several means to enable compilation of trace facilities, in decreasing order of preference:
  • -Dparse.trace
  • --debug or -t
  • put '#define YYDEBUG 1' in the prologue of the grammar file

In C the trace facility outputs messages with macro calls of the form YYFPRINTF (stderr, format, args).

Once you have compiled the program with trace facilities, the way to request a trace is to store a nonzero value in the variable yydebug:

int main(void) {
// With `%define api.prefix {my}`, parser can check MYDEBUG before set yydebug.
#if YYDEBUG==1
    // if tracing info compiled, req for it to be outputed
    yydebug = 1;
#endif
    printf("yyparse returned %d\n", yyparse());
}
